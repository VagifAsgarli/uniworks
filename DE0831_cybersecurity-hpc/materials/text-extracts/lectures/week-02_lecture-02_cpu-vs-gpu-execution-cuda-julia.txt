Two Design Philosophies
CPU: latency oriented  GPU: throughput oriented
Few, very wide, very fast cores  Thousands of simple cores
Deep pipelines, aggressive branch prediction  Shallow pipelines, no speculation
Large multi-level caches per core  Small caches; latency hidden by switching
Most transistors spent on control and cache  threads
Goal: finish one instruction stream as fast as  Most transistors spent on arithmetic units
possible  Goal: keep all arithmetic units busy
A GPU does not make an individual thread fast. It makes having very many threads cheap.
Workloads with few independent tasks, heavy branching, or irregular memory access do not
benefit.

SIMT Execution
CUDA’s execution model is SIMT: single
instruction, multiple threads.
Threads are grouped into warps of 32. All
threads in a warp issue the same instruction in
the same cycle.
If threads in a warp take different branches, the
warp executes both paths and masks off the
inactive threads: branch divergence.

Impact of Divergence on Security Kernels
Cryptographic code is full of data-dependent branching, which is
poorly suited to SIMT execution.
A conditional such as
if key_byte > 0x7f
# path A
else
# path B
end
serialises the two paths within each warp: up to 2× slowdown.
Well-written GPU crypto is therefore branchless, using arithmetic
and bitwise selection instead of control flow.
The same branchless style makes CPU crypto constant-time and
resistant to timing side channels. On GPUs it is a performance
requirement first; lecture 13 returns to the security implications.

Latency Hiding
A global memory access costs ≈ 400–800 cycles. A CPU hides
this with caches and out-of-order execution.
A GPU hides it by oversubscription: when a warp stalls on
memory, the scheduler issues an instruction from a different
resident warp in the same cycle.
The fraction of the hardware’s maximum resident warps that are
actually resident is called occupancy.
GPUs do not avoid latency; they overlap it. This works only if the
scheduler has enough independent work.

The Roofline Model
Operational intensity I = operations performed per byte moved from global memory: FLOP for
numerical code, integer and bit operations for hashing and encryption. Attainable performance is
P = min(Ppeak , I ⋅ Bpeak )

CUDA Platform and Programming Model
CUDA (Compute Unified Device Architecture): the parallel computing platform and programming
model developed by NVIDIA and implemented by NVIDIA GPUs.
First released in 2007. It turned the GPU from a fixed-function graphics device into hardware
programmable for general-purpose computation.
Two things carry the name:
the architecture: the SIMT execution model and memory hierarchy, a property of the silicon;
the platform: driver, runtime, compilers (nvcc, the PTX intermediate representation) and libraries
(cuBLAS, cuFFT, cuDNN, Thrust).
CUDA C/C++ is the reference language: industry-standard C++ plus a small set of extensions for
heterogeneous programming, and an API for device, memory and stream management.
CUDA.jl targets this platform: Julia code is compiled to PTX through LLVM and launched through
the same driver API. The hardware and the execution model are the same; only the front end
differs.

Rationale for Julia in This Course
One language, both sides. The host code and the GPU kernel are ordinary Julia functions. No
separate .cu file, no host/device language split.
Just-in-time specialisation. CUDA.jl compiles kernels through the same LLVM pipeline Julia
uses for the CPU, specialising on the concrete argument types.
Generic code that runs on both. Through multiple dispatch, the same algorithm can execute on
Array and CuArray, essential when you need a CPU reference implementation to validate a
cryptographic kernel against.
Interactive performance work. Profiling, benchmarking and kernel introspection happen in the
REPL, not in a compile–run–inspect cycle.
Everything you learn transfers directly to CUDA C++: the execution model, the memory hierarchy
and the optimisation strategies are properties of the hardware, not of the language.
