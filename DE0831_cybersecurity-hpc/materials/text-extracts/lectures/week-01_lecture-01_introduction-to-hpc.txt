Security Has Become a Throughput Problem
Classical security engineering focused on correctness: protocol
soundness and implementation memory safety.
Modern defensive and offensive security is increasingly about rate:
Password-hash testing throughput
Line-rate packet-inspection capacity
Video-analysis capacity within the incident-response deadline
Log-matching throughput against threat indicators
When a security requirement is expressed as a number of
operations per second, it becomes a high-performance computing
problem.

The Scale of Network Monitoring
A 100 GbE link carries 12.5 GB/s. At the minimum Ethernet frame
size of 64 bytes, that is ≈ 1.5 × 108 packets per second.
A single CPU core at 3 GHz has ≈ 20 clock cycles per packet at
that rate. Deep inspection (regex matching, TLS fingerprinting,
statistical feature extraction) does not fit in 20 cycles.
The classical answers are: sample the traffic (lose visibility), drop to
flow-level metadata (lose detail), or parallelise.
A GPU with ≈ 16 000 CUDA cores gives a very different budget:
≈ 10 core-cycles per packet at the same line rate, if you can
5
express the work as thousands of independent threads.

Definition of High-Performance Computing
High-performance computing (HPC): the branch of computer
science concerned with building and using supercomputers,
parallel algorithms and parallel methods to solve problems that a
single conventional machine cannot solve in acceptable time.
Two situations push a problem into the HPC regime:
Data size constraints. A 10 000 × 10 000 × 10 000 grid holds 1012 points; four Float32
values per point is 32 TB of state, far beyond the memory of any single node.
Time constraints. Weather forecasting, protein analysis, turbulence and flow simulation.
For us, a password audit that must finish before the next credential rotation, or an intrusion
alert that must fire before the attacker moves laterally.
A security answer that arrives after the incident is over has no
operational value. Throughout this course, “fast enough” is defined
against a deadline.

Three Measures of Performance
Theoretical peak Rpeak (also written Rtheor ): the throughput the hardware would deliver if every
functional unit issued an operation every cycle:
Rpeak = fclock × Ncores × FLOP per cycle per core
Example: 3 GHz, 2 cores, 1 FLOP per cycle ⇒ Rpeak = 6 GFLOPS.
Achieved performance Rmax : measured on a specific well-tuned benchmark (the TOP500 list
uses dense linear algebra, HPL).
Sustained performance Rsustained : the throughput achieved by the application.
Rsustained ≪ Rmax ≤ Rpeak
In practice Rsustained < 10% Rpeak is common.
Closing that gap is the subject of lectures 4–7. Quote Rpeak in a report only if you also state the
measured fraction of peak performance.

End of Frequency-Scaling Gains
Moore’s Law (1965, 1975): the number of transistors per chip
doubles roughly every two years. Still approximately holding.
Dennard scaling (1974): as transistors shrink, power density stays
constant, so clock frequency can rise with each generation. Broke
down around 2005.
Consequence: transistor budgets keep growing, but they can no
longer be spent on a faster single core. They are spent on more
cores.
Since about 2005, performance growth is available only to
programs that expose parallelism.

Speedup: Gustafson’s Law
If the problem grows with the machine, the scaled speedup is
S(N ) = (1 − p) + p ⋅ N
Fixed time budget. Gustafson’s law quantifies the amount of
additional work that can be completed within a fixed time budget.
Security workloads are usually Gustafson-shaped: given a faster
machine, the analyst does not finish the same audit sooner; they
audit a larger keyspace, more cameras, or a longer log
retention window.
GPU acceleration therefore changes which security analyses are
feasible, not only how long they take.
