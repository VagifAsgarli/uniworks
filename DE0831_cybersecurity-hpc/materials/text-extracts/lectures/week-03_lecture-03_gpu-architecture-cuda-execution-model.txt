From CPU to GPU: Vector Addition
CPU version, an ordinary Julia loop:
function vec_add!(c, a, b)
@assert length(a) == length(b) == length(c)
@inbounds for i in eachindex(a)
c[i] = a[i] + b[i]
end
end
GPU version, each thread handles one element:
using CUDA
function vec_add_kernel!(c, a, b)
i = (blockIdx().x - 1) * blockDim().x + threadIdx().x
if i <= length(a)
@inbounds c[i] = a[i] + b[i]
end
return nothing
end

Three things to notice:
1. The loop disappeared: it became the grid of threads.
2. blockIdx() and threadIdx() are 1-based in Julia, hence the - 1.
3. @cuda is asynchronous; Array(c) synchronises implicitly.

The Same Work at Three Abstraction Levels
# Level 1 - array programming (lab 2). No kernel written by hand.
c .= a .+ b
# Level 2 - hand-written kernel (lectures 3-6). Full control.
@cuda threads=256 blocks=cld(N,256) vec_add_kernel!(c, a, b)
# Level 3 - vendor-portable kernel (lecture 11). Runs on NVIDIA, AMD, Intel, Apple.
@kernel function vec_add_ka!(c, a, b)
i = @index(Global)
@inbounds c[i] = a[i] + b[i]
end
Always start at level 1. Broadcasting c .= a .+ b compiles to a
single fused kernel that is frequently within a few percent of a
hand-tuned one. Drop to level 2 only where profiling shows it is
needed.

Execution Sequence for @cuda
@cuda threads=256 blocks=1024 my_kernel!(out, in)
1. Compilation (first call only). Julia infers the concrete argument types, specialises my_kernel! for
them, lowers it to LLVM IR, and emits PTX. The result is cached, so subsequent launches are
free.
2. Argument conversion. CuArray arguments are converted to CuDeviceArray, a thin struct holding
a device pointer and dimensions. Kernels therefore cannot allocate or resize arrays.
3. Launch. The driver enqueues the grid on a stream. The call returns immediately; the host
continues running.
4. Scheduling. The GPU work distributor assigns thread blocks to available streaming
multiprocessors as capacity frees up.
Because launches are asynchronous, CUDA.@elapsed or an explicit CUDA.synchronize() is
mandatory before any timing measurement. Without it you measure the launch, not the kernel.

Thread: one instance of the kernel body,

Block: a group of threads placed on a single

Blocks are independent by contract. The hardware may execute them in any order,
concurrently or sequentially, on any SM. This gives CUDA transparent scalability: the same
binary runs on a 20-SM laptop GPU and a 132-SM H100.
There is no grid-wide barrier inside a kernel, so multi-phase algorithms need multiple kernel
launches.

2D and 3D Indexing
function index_2d_kernel!(out, M, N)
ix = (blockIdx().x - Int32(1)) * blockDim().x + threadIdx().x
iy = (blockIdx().y - Int32(1)) * blockDim().y + threadIdx().y
if ix <= M && iy <= N
idx = ix + (iy - Int32(1)) * M  # column-major linear index
@inbounds out[idx] = ix * iy
end
return nothing
end
@cuda threads=(16, 16) blocks=(cld(M,16), cld(N,16)) index_2d_kernel!(out, M, N)
Julia arrays are column-major, unlike C. The first index varies
fastest in memory. For coalesced access, map threadIdx().x (the
fastest-varying thread index) to the first array dimension. Copying
a C or Python kernel verbatim usually gets this backwards and
costs an order of magnitude in bandwidth.

The Mandatory Bounds Check
if i <= length(a)
@inbounds c[i] = a[i] + b[i]
end
blocks = cld(N, threads) almost always launches more threads
than elements. With N = 1000 and threads = 256, four blocks give
1024 threads.
Without the guard, 24 threads write out of bounds. With @inbounds,
that is silent memory corruption, not an error.
Order matters: check the bound with if, then use @inbounds inside.
Never @inbounds the guard itself.

Grid-Stride Loops
function grid_stride_kernel!(A, val)
i = (blockIdx().x - Int32(1)) * blockDim().x + threadIdx().x
stride = gridDim().x * blockDim().x
while i <= length(A)
@inbounds A[i] *= val
i += stride
end
return nothing
end
Decouples grid size from problem size: launch a fixed grid sized to the hardware.
Enables loop-carried register reuse and makes the kernel testable with one block.

Choosing a Block Size
1. Use a multiple of 32. The hardware schedules whole warps. A block of 100 threads occupies 4
warps (128 slots) and wastes 28 of them for the block’s lifetime.
2. Start with 256. 128, 256 and 512 all give good occupancy across architectures; 256 (8 warps) is
the standard default.
3. Respect the resident limits. An SM holds 1536–2048 resident threads. At 1024 threads/block at
most 2 blocks fit on an SM; at 256 threads, 6–8.
4. Watch registers and shared memory. A register-hungry or shared-memory-hungry kernel
reduces the number of co-resident blocks and therefore the occupancy.
CUDA.launch_configuration(kernel.fun) returns the occupancy-optimal block size for the
compiled kernel.

Warps and Warp Scheduling
A block is partitioned into warps of 32 consecutive threads by linear
thread index. This partitioning is fixed at launch.
Each SM has several warp schedulers (4 on recent architectures).
In every cycle, each scheduler picks one eligible resident warp and
issues one instruction for all 32 lanes.
A warp becomes ineligible while waiting for memory, a dependency,
or a barrier.
Zero-cost context switching. Every resident warp keeps its
registers allocated for its whole lifetime, so switching warps costs
nothing.

DE0831 Cybersecurity Solutions in HPC Environment © A. Lektauers 2026.  21
Divergence in Practice
Divergence costs only when threads within the same warp diverge:
# Costly: neighbouring threads take different paths
if i % 2 == 0
out[i] = f(in[i])
else
out[i] = g(in[i])
end
# Free: whole warps take the same path (warp-aligned condition)
if (i - 1) ÷ 32 % 2 == 0
out[i] = f(in[i])
else
out[i] = g(in[i])
end
For security kernels, the usual remedy is to make the code branchless:
mask = UInt32(key_byte > 0x7f) - UInt32(1)  # 0xffffffff or 0x00000000
result = (a & mask) | (b & ~mask)
Both operands are computed unconditionally and one is selected arithmetically.

Role of Occupancy in Performance Optimisation
Higher occupancy gives the scheduler more eligible warps and
therefore better latency hiding, up to a point.
A kernel at 50 % occupancy with generous register allocation and
good instruction-level parallelism routinely beats a 100 %
occupancy kernel that spills registers to local memory.
Occupancy is bounded by whichever resource runs out first:
registers per thread, shared memory per block, or the resident-
block limit.
Rule of thumb: aim for ≥ 50 %, then stop optimising occupancy
and start measuring bandwidth and instruction throughput. Lecture
7 covers the full workflow.

Unintended Float64 Promotion
# WRONG - promotes the whole computation to Float64
@inbounds c[i] = a[i] * 2.0
# RIGHT - stays in Float32
@inbounds c[i] = a[i] * 2.0f0
In Julia, 2.0 is a Float64 literal. Multiplying a Float32 by it promotes
the result to Float64, doubling memory traffic and losing the FP32
throughput. Use the f0 suffix in every GPU kernel.
