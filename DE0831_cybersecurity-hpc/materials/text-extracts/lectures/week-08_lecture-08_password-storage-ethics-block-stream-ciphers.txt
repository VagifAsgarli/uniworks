Salting: Defeating Precomputation
Hashing H(salt ∥ p), a hash H of the salt concatenated with the
password p , stops an attacker from reusing one precomputed table
across users and leaves the cost of a single guess unchanged:
Rainbow tables (precomputed hash → plaintext) become useless: a
table would be needed per salt.
Cross-user attacks: without salt, cracking one hash cracks every user
who chose the same password. With unique salts, each hash must be
attacked separately.

Key Stretching
Key stretching makes one password check deliberately slow by iterating the hash thousands of
times. PBKDF2 (Password-Based Key Derivation Function 2, RFC 8018) iterates HMAC-SHA256
(Hash-based Message Authentication Code: a keyed hash built from two nested SHA-256 calls) c
times, typically 105 ≤ c ≤ 106 .
Cost to the defender: a fraction of a second per login, tuned under expected load. Cost to the
attacker (billions of guesses): multiplied by the iteration count.
Measured on the RTX 4070 SUPER: 3.8 × 104 guesses/s at c = 105 (the table on the next
slide gives the source).
For one implementation the guess rate R(c) at iteration count c scales inversely with c:

Memory-Hard Functions
A memory-hard function needs a large working memory as well as time.
scrypt, Argon2 require a large working memory (tens of MiB) per guess, and every guess
computed at the same time needs its own copy.
Capacity limit: guesses computed at the same time ≲ device memory / memory per guess:
12 GB/64 MiB ≈ 180 on the RTX 4070 SUPER, far fewer than SHA-256 allows. Memory
bandwidth and the dependency between passes cut the rate further.

The Defensive Recommendation
For storing user passwords in 2026:
1. Argon2id is the first choice (memory-hard; its hybrid design limits the side-channel exposure
of the data-dependent variant). Minimum: 19 MiB memory, t = 2, p = 1; raise it to the time
budget of your server, for example ≈ 0.5 s per hash.
2. scrypt (N = 217 , r = 8 , p = 1) where Argon2 is unavailable; bcrypt (cost ≥ 12, input
limited to 72 bytes) as the legacy fallback; PBKDF2-HMAC-SHA256 (≥ 600 000 iterations)
where FIPS 140 (Federal Information Processing Standard) compliance is required.
3. Never a plain fast hash (MD5, SHA-1, SHA-256), salted or not.
4. Always a unique random salt per password (password-hashing libraries generate it).
The minimum parameters follow the Password Storage Cheat Sheet of OWASP (Open Worldwide
Application Security Project), a non-profit foundation that publishes application security guidance.
The measured hash rates above show what each choice costs an attacker.

The Legal Boundary
Under the Latvian Criminal Law:
Section 241: unauthorised access to an automated data processing system.
Section 243: unauthorised interference with a system or data.
Section 244: illegal operations with devices and programs for influencing systems, or with
passwords and access codes, when committed for a criminal purpose (a cracking tool is
covered by the purpose it is used for).
Unauthorised access, interference and misuse of such tools can be criminal offences. Liability
depends on the facts and on the elements of each section.
The Cybercrime Convention (Budapest) obliges its parties to make unauthorised access an
offence in their national law. The EU NIS2 Directive sets the cybersecurity and incident reporting
duties of organisations.

If, in the course of legitimate work, you discover a real vulnerability:
1. Stop. Do not exploit further than needed to confirm it.
2. Document minimally and privately.

Hashing, Encryption and Authentication
Three operations with three different questions
Password hashing: checks a password without recovering it. One-
way, and deliberately slow.
Encryption: conceals data so that only the holder of the key
recovers it. Reversible with the key, and as fast as possible.
Message authentication: lets the receiver detect unauthorised
changes to the data. A short tag, checked before the data is used.
The GPU question is the same for all three: how much of the work is
independent, and how many bytes per second come out.

Modes of Operation
A mode of operation extends a 16-byte block cipher to a whole
message
plaintext  ECB: each block alone  CTR: a counter per block
equal blocks, equal ciphertext  every block differs
ECB (Electronic Codebook) encrypts each block independently, so
identical plaintext blocks produce identical ciphertext blocks and the
outline of the image remains visible. The other modes break the
repetition by their own rule: CBC XORs in the previous ciphertext
block, CTR encrypts a counter.

function chacha20_kernel!(out, inp, key, nonce, counter0)
i = (blockIdx().x - 1) * blockDim().x + threadIdx().x
if i <= length(inp) ÷ 16  # 16 words per 64-byte block
ks = chacha20_block(key, counter0 + UInt32(i - 1), nonce)
for j in 1:16
w = 16 * (i - 1) + j
out[w] = inp[w] ⊻ ks[j]
end
end
return nothing
end
Thread i = keystream block i: counter offset i − 1, no communication
between threads: the starting design
Register use: more registers per thread means fewer active warps; values that
do not fit go to slower memory (lecture 7)
Access pattern: at a fixed j, neighbouring threads touch words 64 bytes apart
