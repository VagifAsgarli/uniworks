Compute-Bound Hashing
A candidate password is generated on the device from an index,
hashed, and compared with a target. Almost nothing crosses the
memory bus.
Operational intensity is enormous: SHA-256 is ≈ 64 rounds of
integer arithmetic per 64-byte block, for a few bytes of I/O.
ISHA-256 ≫ 100 integer operations/byte
Password cracking therefore scales with the number of cores,
which gives the GPU its large advantage over a CPU. Hashing sits
at the far right of the roofline, limited by integer instruction
throughput, not memory.

The Threat Model
A hash turns an input of any length into a fixed-size output called a digest, and cannot be run
backwards. SHA-256 (FIPS 180-4) is the standard example: a 256-bit digest, designed to be fast.
A salt is a random value stored beside the input and mixed in before hashing, so two users with the
same password get different digests.
Example: An attacker who has obtained a database dump holds (salt, hash) pairs, not plaintext
passwords. They mount an offline attack, meaning one run entirely on the attacker’s own hardware:
1. Generate a candidate password p.
2. Compute H (salt ∥ p).
3. Compare with the stored hash.
4. Repeat, billions of times per second, in parallel.
No server is involved, so no rate limit or lockout applies. The only defence is making step 2
expensive enough that the attacker cannot afford enough repetitions. The principal performance
metric is hash rate: how many candidate passwords the attacker can test per second.

Anatomy of SHA-256
64 rounds mix eight 32-bit words, with no branch
on the data
Working state, before the round
a  b  c  d  e  f  g  h
a'  b'  c'  d'  e'  f'  g'  h'
T1 + T2  + T1  After the round
Round function
K[t]
T1 = h + Σ1(e) + Ch(e,f,g) + K[t] + W[t]
T2 = Σ0(a) + Maj(a,b,c)  W[t]
32-bit xor, and, rotate, add mod 2³²: no branch on the data
Σ1(e) = bitrotate(e, -6) ⊻ bitrotate(e, -11) ⊻ bitrotate(e, -25)
Ch(e, f, g) = (e & f) ⊻ (~e & g)  # all UInt32, wrapping add
Thirty-two candidates hash in lockstep across a warp: the control flow of the rounds never depends
on the data, so the rounds do not diverge.

Outline of the GPU Cracking Kernel
function crack_kernel!(found, target, charset, len, base)
idx = (blockIdx().x - 1) * blockDim().x + threadIdx().x
# 1. Map idx -> a unique candidate string over `charset`
#  (base conversion)
# 2. Hash the candidate with an in-register SHA-256
# 3. Compare all 8 words with `target`;
#  on match, record idx in `found`
return nothing
end
Each thread owns one candidate; the index is the password (no
memory traffic).
The SHA-256 state lives entirely in registers.
The comparison is branchless: accumulate an equality mask, write
on full match.

Dictionary and Rule-Based Attacks
Humans do not choose uniformly random passwords. Real
cracking is:
1. Wordlists: leaked password corpora (rockyou, breach compilations).
2. Rules, applied to those words: password → P@ssw0rd!, password2026.
3. Masks for a known structure: ?u?l?l?l?d?d?d?d matches Abcd1234.
4. Markov / ML models: character transition probabilities.
The GPU role is identical: generate candidates on-device, hash,
compare. Only the candidate generator changes.
“Password complexity requirements” often reduce security: they
push users towards predictable patterns the rules exploit.
