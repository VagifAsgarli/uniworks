Track A: Password Auditing
Implement SHA-256 as a GPU kernel and use it to audit a provided set of salted hashes.
Correctness. Before anything else, validate the kernel against the NIST SHA-256 test vectors:
"abc", worked round by round in the NIST example, and the empty string "".
Dictionary attack. Run wordlist.txt (20 000 words) against your hashes_<ID>.txt (200
accounts, user:salt_hex:sha256_hex, digest is SHA-256(salt ‖ password)). Report the recovery
count and the sustained hash rate in H/s.
Rule mangling. Add at least three transformation rules (case, digit suffix, leet substitution).
Report how each changes coverage and cost.
Individualisation. The wordlist is shared by the whole cohort; the hash file is yours.
The hash set is generated by the instructors from synthetic passwords built out of invented
syllables. It contains no real credentials.
About one account in eight uses a 12-character random password that lies outside the supplied
dictionary and rules, so a reported 100 % indicates an error. The realistic ceiling is 85–90 % and
differs between hash files. Base your defensive recommendation on the recovery rate you
measured.

Track B: Data Encryption
Implement one of the following as a GPU kernel and encrypt a large data buffer:
1. AES-128 in CTR mode (S-box in shared or constant memory), or
2. ChaCha20 (pure ARX, register-only).
CTR mode and ChaCha20 parallelise: block i depends only on counter i, so one thread encrypts
one block with no chaining.

Track C: Surveillance Imaging
Generate your scene with gen_footage.jl <YOUR_ID>, then build a GPU pipeline over it and
measure its frame budget.
julia gen_footage.jl 123456  # 1920x1080, 60 frames, ~124 MB
The scene is synthetic: a fixed camera, static structures, three moving objects and sensor noise.
motion_truth_<ID>.csv gives the per-frame bounding boxes, so motion detection is validated
numerically rather than by eye.
Pipeline. Conversion of the UInt8 greyscale frames to Float32, a separable Gaussian blur, Sobel
edge detection, and a motion stage: frame differencing with a threshold.
Memory strategy. Stage tiles through shared memory with correct halo handling.
Correctness. Validate each stage against a CPU reference on a single frame, and your motion
stage against motion_truth_<ID>.csv over the whole clip.
Capacity. Measure the per-frame time, then report how many simultaneous 1080p streams at 25
fps one GPU sustains. Identify the stage that limits it.
The footage is generated, not filmed. No real location or person appears in it, so it meets the
privacy notice in lab 10 and the legal boundary of lecture 9.

Track D: Intrusion Detection
Generate your dataset with gen_ids_dataset.jl <YOUR_ID>, then train a small neural network from
scratch on it.
julia gen_ids_dataset.jl 123456  # 300k train / 75k test, 12 features, 5 classes
Network. A dense network with at least one hidden layer, implemented with your own GPU
kernels or CUDA.jl array operations. Both the forward and the backward pass run on the device.
Correctness. Validate the gradient against a numerical finite-difference check before training
anything.
Evaluation. Report precision, recall and the confusion matrix on test_<ID>.csv, not accuracy
alone. The attack rate is about 1.2 %, so predicting “benign” for everything scores near 98.8 %
accuracy with recall 0. The generator prints this figure as the majority-class baseline for your
classifier.
Capacity. Report inference throughput in flows/s, and state what the measured false-positive rate
produces per day at a stated traffic volume.
The classes overlap on purpose: most attack flows are drawn partway towards normal traffic,
and a few benign hosts are bursty enough to look hostile. A nearest-centroid classifier reaches
recall 0.73 at precision 0.16, so most of its alerts are false positives. The task is to improve on
that trade-off.

Track E: Log Mining
Generate your corpus with gen_logs.jl <YOUR_ID>, then build a parallel matcher over it.
julia gen_logs.jl 123456  # 1M lines, ~120 MB, sshd + nginx events
You get indicators_<ID>.txt (12 addresses and 8 domains) as the matcher’s input, and
truth_<ID>.csv plus entropy_truth_<ID>.csv as ground truth.
Matching. Multi-pattern matching over log lines for a supplied indicator set, with the matched
lines extracted using the scan and compaction primitives from lecture 7.
Entropy flagging. Flag tokens whose Shannon entropy exceeds a threshold, reusing the
scanner from Project 1. Planted payloads sit near 5.3–6.0 bits/char against a normal-token
background of 3.5–4.5. Choose your threshold from your own measured distribution and justify it,
then check against entropy_truth_<ID>.csv.
Correctness. Validate the match set against truth_<ID>.csv over the whole corpus, not a
sample. Indicator lines make up about 0.09 % of the corpus, so a slightly wrong matcher still
looks plausible: compare the full set of matched lines.
Capacity. Report throughput in lines/s and MB/s, then state the daily log volume at which a single
CPU core no longer keeps up and one GPU does.

Requirements for All Tracks
Individualisation. The header block prints your name, student ID, the derived parameters, and
the device name and compute capability. Grading recomputes the parameters, or regenerates the
data, from your ID.
Baseline. A CPU implementation of the same computation, at least single-threaded.
Measurement. The warm-up and CUDA.@elapsed harness from Project 1. Report the sustained
rate across a range of problem sizes: H/s against wordlist size (A), GB/s from 1 MB to 1 GB (B),
at least four input sizes (C to E). Timings taken with @time or @btime around a launch score zero.
Memory layout. Document the layout and show that the main data access is coalesced.
Roofline. Place the dominant kernel on the roofline and state the limiter with evidence. For
integer workloads (A, B, E), an integer-operation count against the device’s integer throughput, or
a bandwidth analysis, is accepted instead.
Reproducibility. Project.toml, Manifest.toml, and a README.md giving the device, the track, the
route, declared AI use, and how to run. A Colab notebook may replace the project files (see
Submission).

Analysis (~1 Page)
1. The headline number for your track: hash rate, cipher throughput or capacity, with the
measurement that produced it and the assumptions it rests on.
2. The limiter. Roofline placement, and the stage or resource that constrains the result, with
evidence: achieved bandwidth, occupancy, CUDA.registers, or Nsight Compute output.
3. Scaling and the transfer wall. How the number changes with input size, where it stops
improving, and how kernel time and host-device transfer time compare. “No crossover observed”
is a valid result when the measurements show it.
4. CPU comparison. Against your single-threaded baseline; a multi-threaded comparison, including
AES-NI and SHA extensions where the CPU has them (A, B), is optional.
5. The defensive conclusion. What a defender should do with this number.
A: a password policy and a storage function with concrete parameters, and the arithmetic that justifies
them.
B: why this implementation must not protect real data, the vetted library to use instead, and a correct
deployment.
C to E: a sizing decision, for example “one A100 covers 42 camera streams, so the 60-camera site
needs two GPUs.”

Authorised Use
Audit only the hash set supplied by the instructors. Encrypt only data you generate or are
given. Never deploy this code to protect real data: production cryptography uses vetted
libraries (libsodium, OpenSSL).
Use only the handout generators for tracks C to E. Do not collect or substitute footage,
network traffic or logs from any real system, network or person, and do not swap in a public
capture dataset without asking first.
Nothing from any track, including recovered plaintexts and generated data, leaves the course.
Reference material: FIPS 180-4; FIPS 197; NIST SP 800-38A; RFC 8439; OWASP Password
Storage Cheat Sheet.
